## 🧭 What Fees101 is

**Fees101 is not a School Management System. It is a School Revenue Operations Platform.**

The bet: remove cash-handling friction (autonomous bank-transfer collection via DVA, manual/cash entry off by default) and remove parent-portal friction (SMS/email instead of a login) — not build a general-purpose school ERP. Attendance, results, timetables, LMS, HR/payroll are explicitly out of scope unless a school forces the question. Everything in this roadmap should be read against that positioning — scope creep toward "manage the whole school" is a deliberate no.

### 🎯 Target: onboard the first real school by **end of November 2026**

Every session works toward that date. Rough intent:
- **Now → build features that don't depend on live Monnify or live messaging** (both are deferred but tracked below).
- **Auth & onboarding come LAST** — no 2FA / friction while testing/logging in daily.
- **Before launch:** fresh DB rebuild, UI rebuild, docs + help center, go-live hardening.

- [ ] **In-product engagement: daily hints + setup guide bot** — **depends on the in-app notification system being built first** (no general notification center exists yet — `admin_notifications` today is a narrow staff-alert table, not a user-facing feed/bell). Two connected ideas, captured here for later design:
  - **"Did you know" daily tips** — a short, dismissible card/toast that shows one random tip about the product each time a user logs in (e.g. "Did you know you can print all of a class's invoices at once to include in report cards?", "Did you know you can send a reminder to just the students who haven't paid?"). Pick randomly from a growing tip pool each session — repeats are fine, the point is passive discovery for features people aren't using, not a guided sequence. Read/dismissed state should persist per-user so a dismissed tip doesn't reappear immediately, but the pool is small enough early on that repeats will happen naturally. Needs: a `product_tips` table or static content list, a per-user "last seen tip" or "dismissed tip ids" record, and the notification/toast surface to render it in once that exists.
  - **Setup guide mascot for new schools** — an animated character (needs its own visual design — a small mascot/bot with personality, not a generic tooltip) that greets a brand-new school's first login and walks them through how the account is set up (academic structure → fee structure → students → first invoice, roughly). Same character doubles as the one "speaking" the daily tips above once onboarding is done, so it becomes a recurring, recognizable presence rather than a one-time wizard. Needs: an onboarding-checklist/progress state per school (so it knows what's already done and doesn't repeat), the mascot's animation/illustration, and a decision on whether it's a fixed step-by-step tour or a "click me for the next thing" companion the user can dismiss and recall.
  - Sequencing: build the notification system first (the delivery mechanism), then the tips content/dismissal state, then the mascot on top — the mascot is presentation/personality on top of the same delivery mechanism, not a separate system.
- [ ] **Parent-facing portal** — parent login to view invoices, balances, pay
- [ ] **Per-student one-off charges** — fines, replacement books, individual exam/late fees as ad-hoc invoice lines. *Deferred: build only if a school asks. Workaround for now = add an optional fee (e.g. "Damages") and leave a note.*
- [ ] **Installment / part-payment plans** — structured "pay in N" schedules (partial payment already works; formal plans deferred until a school needs them)
- [ ] **Automatic late fees** — penalty added when an invoice goes overdue (deferred until requested)
- [ ] **Standalone Payments operations page** — feed, unapplied credits, manual entry, "reconcile now" (overlaps with reporting/analytics above)
- [ ] **Collection-by-class operations page** — drill-down stats (separate from Settings academic structure)
- [ ] **Per-school custom email templates** — Brevo (unlike SES) supports designer/saved templates per sender, so a school could eventually customize wording/branding of their own invoice/receipt/reminder emails beyond just the logo. Deferred until a school actually asks for it.
- [ ] **Per-message channel selection UI** — a "Messages" tab where staff pick a message type (invoice/receipt/reminder) for a student and explicitly choose SMS, email, or both, instead of relying on the default policy. Useful if a parent complains they're not receiving one channel. The channel-override plumbing (`channelOverride` on `sendInvoice`, `sendManualReminder`) already exists per-invoice; this would surface it as its own dedicated page/tab rather than a one-off resend button.
- [ ] **Make the dashboard's Quick Actions panel real** — the mockup's "Record payment / Generate invoice / Send reminder" tiles should each be a genuine standalone action from the dashboard itself (student/invoice picker → the actual flow), not just links out to another page. Needs its own design pass — each action already exists elsewhere in the app (student page, cycles page); the work here is building a well-thought-out consolidated entry point, not new underlying functionality. v2/v3-scale polish, not urgent.
- [ ] **App-wide term/session time-travel view** — a global "viewing: this term / last term / a future draft term" switcher (distinct from the scope selector already on the analytics/payments page, which is comparison-focused rather than "browse the whole app as of a past period") that would let the dashboard — and ideally other pages — show historical data as it stood in an older cycle, the same way you use the app today but looking backward. Explicitly a hard, open-ended one: reasoning through what "the whole app in the past" even means per page (which data is period-scoped vs always-current) is a real design problem, not a quick toggle. Not slotted into any particular version — pick up only when there's nothing higher-priority to work on.
- [ ] **Group classes into arms/streams (e.g. Primary 1A/1B/1C under "Primary 1")** — today each arm is already its own independent `classes` row (confirmed 2026-09-03); there's no schema relationship tying Primary 1A/1B/1C together as "the same grade level," just a shared name prefix by convention. For a big school this matters for organizing/filtering, not fees: each arm has a different class teacher and a different set of students, and bulk operations (e.g. printing all of Primary 1's invoices) currently mean re-sorting students by arm by hand every time instead of the arms already being grouped for you. **Recommended approach:** add a thin *optional* grouping layer on top, not a rework of the class model — a nullable `classes.grade_level_id` (or similar) referencing a new lightweight group table (school-scoped, school names it however they like, e.g. "Primary 1"). Fee structure, promotion mapping, and invoicing all keep working exactly as they do today, unaffected — each arm still has its own fee assignments and its own "promotes to" target, since arms can differ there even if usually mirrored. The group only feeds filtering/sorting/bulk-selection (student list, reports, bulk invoice printing) so a school can act on "the whole grade level" as one unit without losing the per-arm data underneath. Class-teacher assignment is a related but separate gap — no teacher concept exists anywhere in the schema today — track separately, don't bundle into this. **Deferred:** meaningful scope (new table + group-management UI + wiring into student list/reports/bulk-invoice filters) for a need that only bites at bigger-school scale; revisit as a post-V1 "big schools" feature rather than building now.
- [ ] **Per-fee-item payment allocation (pay for "just tuition," track "club" as separately unpaid)** — confirmed 2026-09-03: payments today apply against a student's outstanding invoices as one lump sum, oldest term first (`applyProviderPayment`/`applyPayment.ts`), with no concept of which specific fee line within an invoice got covered. A parent can't pay only tuition and leave club fees outstanding in a way the app understands — it's all just "invoice outstanding amount," so there's no way to know the student is fine for core school access but excluded from a specific paid extra (club, trip, etc.) until that's settled too. Real feature, not a small tweak — would need payments to allocate against specific `fee_items`/invoice line rows rather than the invoice total, a per-item paid/unpaid status, and some UI for a parent (or staff) to choose what a payment is *for* rather than just "pay outstanding balance." Naturally pairs with future WhatsApp/messaging prompts ("pay for club" as its own explicit action/prompt rather than a lump reminder). No design work done yet beyond naming the gap — revisit once there's a settled flow to build it against, not now.

## AI integration — research & plan (not started)

Research + planning only, done 2026-09-16 — nothing in this section is built, and no application code changed as part of this pass. Every item below is a candidate for a future session, not a queued task. Scope check against the "What Fees101 is" section at the top of this file: every idea stays inside School Revenue Operations (fees, invoices, payments, messaging, discounts, data cleanliness) — nothing here pulls toward general school-ERP territory (no AI lesson planning, attendance, results, timetables).

Ranked most to least worth building first: (1) CSV import column-mapping assistant, (2) natural-language Q&A over existing reports/analytics, (3) AI-assisted ad hoc collections messaging, (4) anomaly/fraud review (mostly not an AI problem — see below), (5) WhatsApp/SMS parent chatbot (probably not worth building soon). Cost reasoning below uses Claude's current pricing — Haiku 4.5 at $1/$5 per MTok (input/output) is the cheapest current-generation Claude model and the right fit for every idea here, none of these tasks need a frontier-tier model. GPT-4o-mini/Gemini Flash-class models are comparably cheap alternatives worth a quick bake-off at build time given the standing preference for cheap tooling over expensive defaults — nothing here is provider-locked by anything already in the codebase.

- [ ] **CSV import column-mapping & data-cleanup assistant** — **Priority 1.** Pain point: a Nigerian school's existing student roster usually lives in a spreadsheet whose headers/formats don't match what Fees101 expects — `REQUIRED_FIELDS`/`EXPECTED_HEADERS` in `src/app/(app)/students/import/actions.ts` require an exact header match today ("Guardian Phone" instead of the expected column name fails the whole file with no guidance), on top of inconsistent phone formats and mixed date formats. This is friction at the very first thing a new school does in the app, directly against the end-of-Nov-2026 first-school target. Feasibility: strong fit — `parseAndValidateCSV` already separates parsing/validation from the row-import step, and `processCsvImportChunk` (`src/lib/students/csvImport.ts`) already returns a `failedRows` array for admin review before anything commits, so there's already a human-review checkpoint to slot an AI suggestion into rather than needing to build one from scratch. Approach: on a header mismatch, send only the header row (plus 2-3 sample cell values per column — never full PII rows) to Claude Haiku 4.5 and ask for a best-guess column mapping back as structured JSON; the import screen renders it as an editable "we think column X is Parent Phone — confirm?" step, never auto-committing a mapping. The same small call could flag likely phone-format cleanup as a suggestion ("these look like they need a leading 0"), never an automatic silent rewrite. Cost: a few hundred tokens, once per import file, not per row. Guardrail: a rejected/low-confidence mapping falls back to today's exact-match error — the feature can only reduce friction, never silently miswire a column.
- [ ] **Natural-language Q&A over reports/dashboard data** — **Priority 2.** Pain point: a non-technical bursar wants to ask "which parents haven't paid this term" or "how much did we collect last month" in plain English instead of finding the right export among six report types (`src/lib/reports/reports.ts`) and the right scope on the `/payments` analytics page. Feasibility: the hard, error-prone part — correctly computing figures across term/session scope, credit/discount/cancelled-invoice edge cases — is already built and tested (`reports.ts`, `getDashboardKPIs`/`getCollectionByClass` in `src/lib/queries/dashboard.ts`, the analytics RPCs in `db/analytics_functions.sql`), so the AI's job is narrow: map a question to one of the existing report/analytics functions plus parameters (a fixed tool schema mirroring `ReportType`/`ReportParams`), not generate an answer or compute a number itself. Approach: Claude Haiku 4.5 (bake off against Sonnet 5 if question phrasing needs more nuance) picks a tool + params only; the query still runs through the same already-permission-gated functions, and the rendered answer reuses the existing report/analytics view or CSV export (`toCSV`) rather than LLM-authored prose reciting figures — this is what keeps the model from ever inventing a number. New entry point: a search box on the dashboard or reports page, gated by whichever permission already covers the underlying report. Guardrail: the model receives only the question text and a small typed schema of available reports/scopes — never raw student/payment rows.
- [ ] **AI-assisted ad hoc collections messaging (not the automated reminder ladder)** — **Priority 3.** The brief's framing ("personalize debtor reminders") turns out to be a narrower gap than it looks: the existing automated advance/due/overdue cadence already has tone-appropriate, cost-tuned, deterministic templates (`composeReminderSMS`/`composeOverdueSMS` in `src/lib/messaging/composeInvoice.ts` — sub-250-char, GSM-7-safe, "NGN" not "₦" to keep SMS encoding cheap) that an LLM would only make slower, costlier, and less predictable to reproduce, with real hallucination risk on a message about real money going to a real parent. The actual gap: nothing helps an admin draft the harder, one-off case the fixed ladder doesn't cover — a firm-but-not-aggressive note to a specific list of long-overdue families, or a one-off class-wide announcement. Feasibility: the send/delivery-logging path already exists (`sendMessageWithFallback`, `src/lib/messaging/sendMessage.ts`) and already supports manual, admin-triggered sends — an AI drafting step only needs to sit in front of it as a text generator. Approach: a "Draft a message" helper on the debtors report or a student page — admin picks a tone and a target list, Claude Haiku 4.5 drafts SMS/email text within the same length/encoding constraints already documented in `composeInvoice.ts`; the admin edits and explicitly sends via the existing action, so delivery logging/fallback behavior is unchanged. Guardrail: no draft is ever sent without an explicit admin click (same pattern as the existing "Notify parent of update" button); the model is only ever given the amount/name/term already computed server-side, never asked to compute a balance itself, so it cannot hallucinate a wrong figure into a parent-facing message.
- [ ] **Anomaly/fraud signal review — mostly a statistics problem, not an AI one** — **Priority 4.** Pain point: the sibling-discount fraud vector this roadmap already documents at length (`addStudent()`'s family-matching does exact-string phone matching only, no normalization or secondary identity check, confirmed exploitable during the 2026-09-16 stress test) is real, and sibling discounts are auto-applied purely off `family_id` grouping (`computeSiblingDiscount` in `src/lib/discounts/compute.ts`) with no cross-check. Honest take: the actual fix here — phone-number normalization, fuzzy name matching across families sharing a phone, simple statistical bounds on payment amounts (this roadmap already reproduced a ₦9,999,999,999 test payment sailing through with zero anomaly flag anywhere) — is plain deterministic code, not an LLM feature, and should be built as such on its own merits (PII never has to leave the server to do it). Where AI could add something real, once that deterministic layer exists: taking an already-flagged, already-reduced list of suspected matches ("Family A and Family B share a phone number; surnames differ") and turning it into a short plain-English weekly digest for the owner instead of a raw table, using Claude Haiku 4.5 as a summarizer, not a detector. Approach if built: a periodic digest (reusing the existing cron/background-job pattern) surfaced on Recent Activity or a dedicated review list; the model never sees unreduced PII and never takes action — purely descriptive, all follow-up goes through the existing discount-approval/revocation flows. Priority reasoning: build the deterministic matching fixes first regardless of any AI decision — they're a data-integrity fix this roadmap already calls for elsewhere — and only add the LLM summary layer later if flagged-item volume grows enough to need digesting.
- [ ] **WhatsApp/SMS chatbot for parent balance inquiries — likely not worth building soon** — **Priority 5 (lowest).** Pain point as framed: a parent (no login, by design) texts "how much do I owe" and gets an instant answer instead of calling the school office. Honest take: this conflates two different problems. (a) "What's my balance" is a fixed lookup by phone number — not an LLM problem at all; a keyword-triggered inbound webhook that queries `families`/`invoices` and replies with a template is cheaper and more reliable than routing it through a model. (b) Free-form Q&A ("why did my total change," "can I pay in installments") is where an LLM would matter, but it requires solving parent identity verification over an unauthenticated inbound channel that doesn't exist today — the product deliberately has no parent login, so there's no auth primitive to reuse, and a wrong-number match would disclose one family's balance to another. Feasibility given today's data model: messaging is currently outbound-only (invoice/receipt/reminder sends); no verified two-way channel exists, and WhatsApp itself is already listed elsewhere in this roadmap as deferred pending the next school onboarding, on top of its own per-conversation Nigeria pricing tier. This is also the one idea on this list where a human-in-the-loop check isn't really possible per-message — a real-time reply either goes out immediately with the right balance or it isn't a useful chatbot. Recommendation: build the zero-LLM fixed-lookup version (a) first if/when WhatsApp ships, gated behind an identity check (e.g. last-4-of-admission-number) before disclosing any balance, and only reconsider an LLM layer for free-form questions after that identity problem is actually solved — don't build the chatbot as an AI project first.
