## 🧭 What Fees101 is

**Fees101 is not a School Management System. It is a School Revenue Operations Platform.**

The bet: remove cash-handling friction (autonomous bank-transfer collection via DVA, manual/cash entry off by default) and remove parent-portal friction (SMS/email instead of a login) — not build a general-purpose school ERP. Attendance, results, timetables, LMS, HR/payroll are explicitly out of scope unless a school forces the question. Everything in this roadmap should be read against that positioning — scope creep toward "manage the whole school" is a deliberate no.

### 🎯 Target: onboard the first real school by **end of November 2026**

Every session works toward that date. Rough intent:
- **Now → build features that don't depend on live Monnify or live messaging** (both are deferred but tracked below).
- **Auth & onboarding come LAST** — no 2FA / friction while testing/logging in daily.
- **Before launch:** fresh DB rebuild, UI rebuild, docs + help center, go-live hardening.

## ⚡ Scale & reliability

For schools of 500–1,000+ students on Vercel serverless. (No Monnify/messaging dependency — safe to build now.)
Still just Next.js + Supabase + Vercel throughout — no new infra needed. "Background job" here means: a
status/progress row in Supabase that the client polls, work picked up by a Vercel Cron-triggered route (or
simply a higher `maxDuration` on the route), not a separate server.

- [~] **Auth round-trip latency (per-click slowness)** — **partially fixed.** Every navigation used to make 4 sequential Supabase round-trips before page data: middleware `auth.getUser()` (network) + an `is_active` DB lookup, then `getAuthContext()` `auth.getUser()` **again** + a user/roles lookup. Done: (1) removed the redundant middleware `is_active` lookup (`getAuthContext` + `has_permission()` still enforce it); (2) both `auth.getUser()` → `auth.getClaims()` (local JWT verification once a session's token is ECC-signed). For a big school this matters for organizing/filtering, not fees: each arm has a different class teacher and a different set of students, and bulk operations (e.g. printing all of Primary 1's invoices) currently mean re-sorting students by arm by hand every time instead of the arms already being grouped for you. **Recommended approach:** add a thin *optional* grouping layer on top, not a rework of the class model — a nullable `classes.grade_level_id` (or similar) referencing a new lightweight group table (school-scoped, school names it however they like, e.g. "Primary 1"). Fee structure, promotion mapping, and invoicing all keep working exactly as they do today, unaffected — each arm still has its own fee assignments and its own "promotes to" target, since arms can differ there even if usually mirrored. The group only feeds filtering/sorting/bulk-selection (student list, reports, bulk invoice printing) so a school can act on "the whole grade level" as one unit without losing the per-arm data underneath. Class-teacher assignment is a related but separate gap — no teacher concept exists anywhere in the schema today — track separately, don't bundle into this. **Deferred:** meaningful scope (new table + group-management UI + wiring into student list/reports/bulk-invoice filters) for a need that only bites at bigger-school scale; revisit as a post-V1 "big schools" feature rather than building now.
- [ ] **Per-fee-item payment allocation (pay for "just tuition," track "club" as separately unpaid)** — confirmed 2026-09-03: payments today apply against a student's outstanding invoices as one lump sum, oldest term first (`applyProviderPayment`/`applyPayment.ts`), with no concept of which specific fee line within an invoice got covered. A parent can't pay only tuition and leave club fees outstanding in a way the app understands — it's all just "invoice outstanding amount," so there's no way to know the student is fine for core school access but excluded from a specific paid extra (club, trip, etc.) until that's settled too. Real feature, not a small tweak — would need payments to allocate against specific `fee_items`/invoice line rows rather than the invoice total, a per-item paid/unpaid status, and some UI for a parent (or staff) to choose what a payment is *for* rather than just "pay outstanding balance." Naturally pairs with future WhatsApp/messaging prompts ("pay for club" as its own explicit action/prompt rather than a lump reminder). No design work done yet beyond naming the gap — revisit once there's a settled flow to build it against, not now.
